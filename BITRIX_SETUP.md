ранее внесённая декоративная панель — 2 шт. В SQLite подтверждены оба этапа,
`bitrix_skipped=false`. Видеозапись или приглашение проверяющего ещё нужно подготовить.

## Что должно быть в портале

С 08.11.2026 добавлен реестр [«Пользователи бота»](https://b24-4ituhe.bitrix24.by/crm/type/1048/list/category/0/)
(`entityTypeId=1048`) и включён `BITRIX_ACCESS_ENABLED=true`. Профиль владельца
перенесён с действующим доступом и ролью администратора.

### Профили, роли и доступ

| Роль | Возможности |
|---|---|
| Администратор | Отчёты, исправления, вопросы к таблице; команда `/users` открывает реестр управления пользователями |
| Мастер | Отчёты, исправления и вопросы по общему объекту; управление пользователями недоступно |

Чтобы подключить сотрудника:

1. Сотрудник пишет боту `/start`. При закрытом доступе бот показывает его **числовой Telegram ID**.
2. В реестре нажать «Создать». В названии указать ФИО, заполнить Telegram ID,
   выбрать роль. Username, должность, объект и комментарий можно заполнить дополнительно.
3. Включить «Доступ к боту разрешён» и сохранить карточку.
4. Сотрудник снова пишет `/start`. Бот показывает назначенную роль и принимает команды.

Для отключения снять «Доступ к боту разрешён». Проверка выполняется через REST
при каждом обращении; положительный доступ не кешируется. Перезапуск бота не нужен.
Старая персональная ссылка на отчёт также блокируется. Пустая роль, незнакомый ID,
дубликаты одного Telegram ID и недоступность REST закрывают доступ. Новая карточка
по умолчанию не имеет включённого доступа. По username доступ не выдаётся.

Роли бота и права входа в портал Битрикс24 — отдельные вещи. Мастеру не создаётся
учётная запись портала. Управлять карточками сотрудников в Битрикс24 должен
пользователь с административными правами на этот реестр. Роль администратора в боте
показывает `/users`, но сама по себе не выдаёт права CRM и не приглашает человека в портал.
Поле «Объект» пока информационное: этот экземпляр бота обслуживает одну общую Google-таблицу.

При включённом реестре `ALLOWED_USER_IDS` не обходит решения CRM. Он остаётся списком
исходных владельцев для первичного переноса и старого локального режима. Точные
REST-имена полей и ID вариантов ролей находятся в локальных `BITRIX_USERS_FIELDS`,
`BITRIX_USERS_ENTITY_TYPE_ID`, `BITRIX_USER_ROLES`; менять их при обычной смене роли не нужно.
Скрипт `python -m m100_bot.bitrix_workspace` воспроизводит поля и формы. Для него
временно нужен scope `userfieldconfig`; работающий бот использует только CRM.

### Оформление и контроль отчётов

В карточке дневного отчёта настроены разделы: «Отчёт об объекте», «Кто и когда»,
«Выполнено за день», «Контроль сметы», «История изменений» и «Служебные данные».
Отдельные поля даты, автора, времени, количества позиций, превышений и статуса
можно использовать в колонках и фильтрах списка. Длинный внешний ключ и текст
истории находятся внутри карточки. Компактные колонки обоих реестров применены
для всех пользователей; карточки разделены на тематические блоки. В левое меню
владельца добавлены быстрые переходы к отчётам и пользователям бота.

Новые операции сохраняют имя сотрудника из профиля и точное время. История объёмов
показывает каждую операцию: автор, время, позиция, было → стало. Повтор сохранения
не добавляет вторую запись истории. Для старых операций без сохранённого времени
показывается «Время не сохранено»; при переносе существующей карточки время её
последней записи берётся из уже известного времени обновления CRM.

«Превышений сметы» — количество позиций, где накопленное выполнение больше сметы.
«Близко к завершению» — позиции с положительным остатком работ до 10% сметы.
Завершённая ровно по смете позиция не считается превышением. Это не складской
остаток материалов: поступления, выдачи и закупки пока не ведутся.
Показатели обновляются после сохранения отчёта ботом; ручное изменение Google
без нового сохранения не запускает фоновую синхронизацию.

Статус проверки — «На проверке», «Принят», «Нужно уточнение». Проверяющий меняет
его в карточке CRM и оставляет замечание. Новая операция возвращает статус
«На проверке», технический повтор той же операции сохраняет выставленный статус.
Статус проверки — управленческая отметка; подтверждённые объёмы уже записаны в Google.

Проверено 08.11.2026: действующий администратор, смена на мастера, отключение и
восстановление доступа через настоящий REST. На работающем сервере
проверена старая ссылка отчёта: 200 → отключение профиля → 403 → восстановление → 200.
169 автотестов проходят, включая запрет Google-записи после отзыва доступа. Временный scope настройки
полей после создания структуры удалён; проверка CRM продолжает работать.

Дневные отчёты хранятся в одном смарт-процессе в режиме «Список», доступ — в отдельном
реестре пользователей. Отдельные сделки, лиды, контакты, товары, роботы,
бизнес-процессы и платные приложения для задания не нужны.

| Поле | Что хранится | Кто заполняет |
|---|---|---|
| Название (`title`) | `Дневной отчёт · 07.11.2026` | Бот |
| Работы за день (`ufCrm_8_M100_WORKS`) | Полный актуальный список работ за день: название по спецификации, объём, единица; ID операции; ссылка Google Sheets | Бот |
| Внешний ключ, одиночная строка | `m100:<spreadsheet_id>:<YYYY-MM-DD>` | Бот |
| ID, автор, время создания/изменения | Системные реквизиты карточки | Битрикс24 |

Коды пользовательских полей: `UF_CRM_8_M100_KEY` и `UF_CRM_8_M100_WORKS`.
Проверенные точные REST-имена: **`ufCrm_8_M100_KEY`**, **`ufCrm_8_M100_WORKS`**.
Поле работ — строка с 12 строками ввода. У этого смарт-процесса отсутствует
стандартное поле `comments`; поэтому в адаптер добавлен `BITRIX_REPORT_FIELD`.
На другом процессе, где `comments` доступно, можно оставить значение по умолчанию.
Для `.env` нужно **точное имя из ответа `crm.item.fields`**, а не подпись «Внешний ключ».
Утилита `provision` получает его автоматически по `upperName`; она не угадывает camelCase.
В API пользовательских полей `entityId=CRM_8`, а в `crm.item.*` — `entityTypeId=1040`.
Это разные идентификаторы.

Одна карточка соответствует одной Google-таблице и дате, включая отчёты нескольких
мастеров в эту таблицу. Новое подтверждение за тот же день обновляет существующую
карточку полным дневным итогом. Нулевые позиции исключены; при полном обнулении
сохраняется сообщение «Все дневные объёмы обнулены».

## Создание портала и доступность API

1. Зарегистрировать отдельный тестовый портал Битрикс24. Подтверждение почты,
   пароль и принятие соглашений выполнить самостоятельно в браузере.
2. В «Мой тариф» проверить доступность смарт-процессов и REST. Для этого портала
   включён бесплатный деморежим на 15 дней. После его окончания функциональность
   может ограничиться; учесть это при сроке проверки работодателем.
3. В разделе «Приложения → Разработчикам» открыть создание входящего вебхука.
   Название: «М100 — дневные отчёты». Для работы бота нужен scope **CRM (`crm`)**.
   Для автоматического создания полей утилитой дополнительно нужен
   **Настройка пользовательских полей (`userfieldconfig`)**; при ручном создании
   поля этот scope боту не требуется.
4. Вебхук выполняет запросы от имени своего владельца. В тестовом портале его
   владелец должен видеть процесс и иметь право добавлять/изменять карточки.
   Создание процесса/поля требует прав изменения настроек CRM.
5. Вебхук — секрет. Не открывать его REST-URL в адресной строке, не включать в
   видео, скриншоты, Git, React/Vite-переменные или сообщения чата.

Требования зависят от региона/тарифа. По официальной документации для REST может
потребоваться активная подписка Маркетплейса или её пробный режим. Если API
недоступен, сначала проверить фактическое сообщение портала и возможности демо.
Покупку подписки согласовывать отдельно; не обещать вечную бесплатную работу.

## Подключение к существующему боту

Команды выполняются из корня проекта; `uv run python` можно заменить
на `.venv/bin/python`. Существующий `.env` не заменять шаблоном.

```sh
# Скрытый ввод: вставьте вебхук в терминал, он не отображается и не входит в команду.
uv run python -m m100_bot.bitrix_setup webhook

# Только чтение: проверить API и получить доступные процессы.
uv run python -m m100_bot.bitrix_setup inspect

# Создать/найти процесс и внешнее поле, получить точное REST-имя и сохранить ID в .env.
uv run python -m m100_bot.bitrix_setup provision

# Настоящие добавление, изменение и повтор через тот же адаптер, что использует бот.
uv run python -m m100_bot.bitrix_setup verify

# Повторно проверить запись и включить BITRIX_ENABLED=true только после успеха.
uv run python -m m100_bot.bitrix_setup enable

# Проверить чтение Google и процесса Битрикс24, затем перезапустить бота.
uv run m100-check --remote
```

Утилита меняет только нужные строки `BITRIX_*`, сохраняет остальные настройки и
комментарии, устанавливает `.env` права `600`. Значения секретов не печатает.
`inspect` работает и при `BITRIX_ENABLED=false`. `provision` не включает интеграцию.
Если процесс уже существует, его ID нужно оставить в `.env`; утилита не создаёт
другой процесс при недоступности настроенного ID. При повторе создания поле
находится по своему исходному коду. Во время настройки запускать только одну копию утилиты.

Для сохранения работающему боту нужны следующие настройки:

```dotenv
BITRIX_ENABLED=true
BITRIX_WEBHOOK_URL=<секретный входящий вебхук, заполняется локально>
BITRIX_ENTITY_TYPE_ID=1040
BITRIX_EXTERNAL_KEY_FIELD=ufCrm_8_M100_KEY
BITRIX_REPORT_FIELD=ufCrm_8_M100_WORKS
```

Команда `verify` записывает только Битрикс24, не меняет Google Sheets или SQLite.
Используется дата **31.12.2099**, отдельная от реальных дневных отчётов. В карточке
есть явная метка «ТЕСТ ПОДКЛЮЧЕНИЯ М100 — не выполненные работы».
Последовательность: 15 м → 20 м → повтор 20 м. После каждого шага API должен
вернуть ровно одну карточку с тем же ID и ожидаемым текстом. Повтор команды
обновляет эту же тестовую карточку. Если дата занята посторонней записью,
проверка останавливается. Карточка остаётся для проверки; автоматического удаления нет.

Не выдавать результат `verify` за полную демонстрацию Telegram: это проверка
реального REST и адаптера. Для сдачи дополнительно пройти сценарий через бота.

## Поведение при исправлениях и сбоях

Бот сначала сохраняет Google Sheets, затем читает полный дневной итог и вызывает
`crm.item.list` по внешнему ключу. При отсутствии карточки — `crm.item.add`, при
наличии — `crm.item.update`. Если найдено несколько карточек с одним ключом,
бот останавливается и просит проверить портал.

Между Google и Битрикс24 нет общей транзакции. Этапы сохраняются в SQLite.
Если Google уже записан, а Битрикс24 не ответил, использовать повтор текущей
операции (`повтори` или доступное действие повтора). Повтор **не прибавляет объёмы
заново в Google**. Не отправлять тот же отчёт как новый: это отдельная операция
добавления. Не удалять SQLite и не запускать несколько записывающих копий бота.
Внешнее поле не имеет серверного ограничения уникальности: защита рассчитана
на одну копию бота с её блокировкой записи, а не на параллельные независимые системы.
