# Проверка М100: от запуска до приёмки

Актуально: 08.11.2026. Рабочее хранилище — PostgreSQL. SQLite используется только
одноразовым импортёром старой базы. Демо-режима в сайте нет.

## 1. Что уже запущено на этом компьютере

- Telegram: https://t.me/m100_work_reports_bot
- Рабочий сервер и API: http://127.0.0.1:8765
- Интерфейс разработки: http://127.0.0.1:5173
- Проверка сервера: http://127.0.0.1:8765/healthz
- PostgreSQL: база `m100`; тесты используют `m100_test` с отдельной схемой на тест.

Ожидаемый ответ `/healthz`: `{"status":"ok","database":"postgresql"}`.
`starting` означает, что новая копия ждёт завершения старого писателя при обновлении.
Изменять отчёты в этот момент нельзя; повторите через несколько секунд.

Главная страница намеренно не показывает чужие отчёты. Отправьте `/report` или
`/draft` боту и откройте его персональную ссылку. Вручную придумывать ID или токен не нужно.

## 2. Повторяемая установка

Из корня проекта:

```sh
uv sync --frozen
npm ci --prefix web
npm run build --prefix web
```

Скопируйте `.env.example` в `.env` только при новой установке. Не затирайте настроенный `.env`.
Нужны токен Telegram, доступ Google, ключ и модель LLM, Битрикс24 и `DATABASE_URL`.

Локальный PostgreSQL, установленный через Homebrew:

```sh
brew services start postgresql@16
createdb m100
createdb m100_test
```

`createdb` выполняется один раз; сообщение «already exists» не требует удаления базы.
Для этой конфигурации в `.env`: `DATABASE_URL=postgresql:///m100`.

Вариант через Docker, если локального PostgreSQL нет:

```sh
docker compose up -d postgres
docker compose exec postgres createdb -U m100 m100_test
```

В `.env` для запуска Python на хосте:
`DATABASE_URL=postgresql://m100:m100_local@127.0.0.1:5433/m100`.
При изменённом `POSTGRES_PASSWORD` используйте свой пароль. У Compose отдельный
порт 5433, чтобы не конфликтовать с локальным PostgreSQL на 5432.

Проверка и запуск:

```sh
uv run m100-check --remote
scripts/start.sh
```

Если бот уже работает, второй экземпляр не запускайте. Блокировка PostgreSQL
защищает ту же исходную таблицу от второго писателя. Проверка `m100-check --remote`
читает Google/Битрикс и проверяет PostgreSQL, но не записывает выполненные объёмы.

## 3. Миграция старой SQLite-базы

На этом компьютере миграция уже выполнена. Старый файл и резервная копия сохранены
в `data/`; содержимое шести таблиц сверено. Действующие персональные ссылки сохранены.

Для другой установки:

1. Остановите старый бот, чтобы новые операции не появились после снимка.
2. Создайте пустую PostgreSQL-базу и задайте её `DATABASE_URL`.
3. Выполните:

```sh
uv run python -m m100_bot.migrate_sqlite data/bot.sqlite3
uv run m100-check --remote
```

Импорт создаёт отдельную резервную копию, проверяет модели и числа строк, выполняет
перенос одной транзакцией. Повтор того же импорта распознаётся; чужая непустая база
не перезаписывается. Исходная SQLite-база не изменяется. После запуска нового бота
источником актуальных данных становится PostgreSQL: старая SQLite-копия больше не обновляется.

## 4. Автотесты без реальных записей

Для Homebrew-конфигурации:

```sh
export TEST_DATABASE_URL=postgresql:///m100_test
uv run pytest -q
npm test --prefix web
uv run ruff check src tests scripts
npm run build --prefix web
```

Для Docker замените первую команду на:

```sh
export TEST_DATABASE_URL=postgresql://m100:m100_local@127.0.0.1:5433/m100_test
```

Тесты создают случайные схемы `pytest_*` и удаляют только их. Google, Битрикс и
Telegram в серверных автотестах подменены; PostgreSQL настоящий. Покрываются
доступ, ревизии, повторные клики, перезапуск, частичное сохранение, расчёты,
импорт, старые ссылки и атомарность. Ошибка подключения к тестовой базе — ошибка
запуска тестов; незаметного перехода на SQLite нет.

## 5. Проверка настоящей LLM без записи объёмов

Эти команды используют настроенный LLM API и расходуют его лимит:

```sh
uv run python scripts/evaluate_recognition.py
uv run python scripts/check_agent_commands.py
uv run python scripts/check_table_queries.py
```

Первая команда читает текущий каталог и проверяет 30 эталонных фраз из
`evals/recognition.json`: позиции, объёмы, связанные работы, дроби, неоднозначности
и несовпадение единиц. Отчёт: `artifacts/recognition-results.json`; ненулевой код
выхода означает несовпадение. Это проверка текста, не качество шумного аудио. Дополнительно проверено синтетическое
голосовое `artifacts/voice-test.wav`: расшифровка и все шесть позиций совпали с
примером задания; результат сохранён в `artifacts/voice-recognition-result.json`.
Один успешный прогон не гарантирует безошибочность модели на новых фразах.

Две остальные команды проверяют по 10 шагов диалога с настоящей LLM,
PostgreSQL в изолированной схеме и имитацией внешних записей. Они не отправляют
сообщения в Telegram и не меняют рабочие Google Sheets/Битрикс24.
При изменении спецификации адаптируйте эталонные ID к отдельному контрольному каталогу,
а не меняйте ожидаемые ответы ради успешного прогона.

## 6. Визуальная проверка с гарантированным сбоем Битрикс

```sh
uv run python scripts/browser_sandbox.py
```

Откройте адрес из `artifacts/browser-sandbox-url.txt`. Это локальный сервер на 8766,
отдельная схема PostgreSQL и имитация внешних систем, без загрузки рабочего `.env`.

1. Видно предупреждение: осталось 5 м, вводится 8 м, превышение 3 м.
2. Откройте карточку. Название, единица, смета и ставки доступны только для просмотра;
   меняются выполненный объём и выбранная позиция.
3. Нажмите «Сохранить отчёт». Появится отдельное подтверждение превышения. «Проверить объём»
   возвращает к отчёту без записи.
4. Подтвердите «Сохранить с превышением». Первая отправка Битрикс специально завершится
   ошибкой. Видно: Google сохранён, Битрикс ожидает повторной отправки.
5. Нажмите «Повторить сохранение». Обе системы станут сохранёнными. Объём останется 8 м,
   другая сохранённая работа остаётся 2 шт, повторного прибавления нет.
6. Нажмите «Исправить за сегодня». Откроется черновик дневного итога: 8 м и
   другая работа 2 шт. Измените 8 на 4 через «Применить», затем «Сохранить отчёт».
   В сводке должно быть 4 м и прежние 2 шт, а не 12 м.
7. Для замены позиции откройте карточку, введите количество и нажмите «Заменить работу».
   Выберите «Кабель для замены»: введённый объём должен сохраниться. До «Применить»
   изменения существуют только в открытой панели; до «Сохранить отчёт» — только в черновике.
8. Нажмите Ctrl+C в терминале стенда: его схема удалится. Стенд не включён в рабочий сайт.

Синхронизация сайта и Telegram проверяется интеграционным тестом
`test_browser_clarification_and_save_are_authoritative_for_bot` в `tests/test_commands.py`:
он уточняет неоднозначную работу через API сайта, сохраняет её, проверяет состояние,
переданное модели бота, и начинает новый отчёт без старых вопросов или повторной записи.
`test_starting_new_work_keeps_a_genuine_pending_report` проверяет сохранность настоящего
незавершённого черновика. Оба теста используют отдельную схему PostgreSQL и имитацию Telegram.

В браузере дополнительно проверьте изменение из бота при открытом сайте: новая ревизия
должна появиться после возвращения в окно или в течение 5 секунд. Во время ввода в карточке
фоновое обновление приостанавливается. Если бот успел изменить ту же работу, «Применить»
покажет конфликт, сохранив введённый текст; после закрытия карточки загрузится актуальный отчёт.

## 7. Приёмка через настоящего Telegram-бота

Для этого этапа используйте выделенную контрольную Google-таблицу и тестовый процесс
Битрикс24. Дальнейшие подтверждения действительно меняют объёмы. Зафиксируйте исходные
значения, чтобы затем вернуть дневной итог через `/today`, сохранив неназванные работы.

| Шаг | Что сделать | Что должно произойти |
|---|---|---|
| Доступ | Отправить `/start` разрешённым пользователем | Реальный профиль, меню и таблица |
| Основной ввод | Отправить текст из примера ниже | Шесть правильных строк; до подтверждения записи нет |
| Голос | Произнести тот же текст голосовым Telegram | Та же структура и объёмы, доступна расшифровка |
| Правка | Открыть отчёт, изменить 15 на 16, нажать «Применить» | Меняется черновик; общий отчёт ещё не записан |
| Подтверждение | Нажать общую кнопку «Сохранить отчёт» | Дата/ячейки Google обновлены, Битрикс содержит дневной итог |
| Повтор | Повторить подтверждение того же отчёта | Объёмы не удваиваются, карточка Битрикс одна |
| Уточнение | «Поставили десять хомутов и двадцать метров кабеля» | Вопросы о диаметре/типе и сечении; нет угадывания |
| Продолжение | Уточнить «хомуты под фреон, кабель три на полтора» | Исправляются те же строки, количество сохраняется |
| Существующие данные | «Исправить за сегодня» на сайте или `/today` в боте; исправить одну работу | Заменяется её дневной итог; остальные позиции сохранены |
| Удаление | Удалить работу из дневного итога и подтвердить | Для неё записан ноль; остальные объёмы не исчезли |
| Остатки | «Сколько осталось кабеля три на два с половиной?» | Ответ по реальной таблице, без записи |
| Превышение | В черновике указать объём выше реального остатка | Предупреждение до записи, отдельный обзор на сайте |
| Немедленная запись | Добавить работу «и сразу сохрани» | Без превышения сохраняется; с новым превышением остаётся черновик на проверку |
| Потеря сети | Отключить интернет перед подтверждением, затем вернуть | Понятная ошибка, безопасный повтор; Google/Битрикс не дублируются |
| Перезапуск | Оставить черновик, перезапустить бот, `/draft` | Черновик и история сохранились в PostgreSQL |
| Чужой доступ | Открыть отчёт с изменённым ID/без токена | 401/403, никаких данных и записей |
| Отзыв роли | Отключить пользователя в реестре Битрикс24 | Старые персональные ссылки также перестают разрешать операции |

Основной пример:

> Сегодня проложили медь 6-ку 15 м и 9-ку 15 м, изоляцию на них столько же,
> кабель 3х2,5 — 56 м, поставили 10 хомутов под фреон.

Ожидание для контрольной спецификации: `OV3-012=15`, `OV3-013=15`,
`OV3-015=15`, `OV3-016=15`, `EM3-002=56`, `OV3-037=10`.

Проверьте голос трижды: тихая комната, обычная речь с паузами/оговорками,
умеренный фоновый шум. Ошибка или сомнение должны приводить к уточнению,
а исправление — менять ту же работу. Неразборчивую речь бот не должен выдавать за сохранённый отчёт.

## 8. Railway

В репозитории подготовлены `Dockerfile`, `.railway/railway.ts`, `/healthz`, поддержка `PORT`,
`DATABASE_URL`, Google-ключа из секретной переменной и PostgreSQL-блокировки писателя.
Целевой проект: [M100](https://railway.com/project/df1cf821-dfa0-4222-a0c5-81a472e2cc6b),
рабочее пространство Test Test's Projects. Адрес: https://m100-production.up.railway.app.
Сервисы: `m100` (бот + сайт) и `Postgres` (постоянный том, приватная сеть).
Автодеплой: `main` → GitHub Actions `Checks` → Railway с включённым Wait for CI.

1. Создайте проект и PostgreSQL в Railway, сервис приложения — из этого репозитория,
   корень сборки — корень проекта, сборщик — Dockerfile.
2. В переменные приложения внесите секреты из локального `.env` через защищённую форму,
   `DATABASE_URL=${{Postgres.DATABASE_URL}}` (имя сервиса БД должно совпадать),
   `GOOGLE_CREDENTIALS_JSON` = полное содержимое ключа, `GOOGLE_CREDENTIALS_FILE` = пусто.
3. `WEB_HOST=0.0.0.0`, `WEB_AUTO_OPEN=false`, `WEB_ENABLED=true`, `PORT=8080`.
   `TELEGRAM_MODE=webhook`, случайный `TELEGRAM_WEBHOOK_SECRET` длиной 32–256 символов.
   Сервер сам регистрирует HTTPS-вебхук; секрет не должен совпадать с токеном бота.
4. Одна реплика приложения. Новая копия стартует в состоянии `starting`, блокирует
   изменения и ждёт освобождения писателя; после остановки старой становится `ok`.
5. Сгенерируйте HTTPS-домен приложения и задайте его как `WEB_BASE_URL`.
   Схема PostgreSQL создаётся автоматически. Для переноса существующих данных используйте
   резервную копию/восстановление PostgreSQL в пустую целевую базу при остановленном боте.
6. Перед запуском Railway-копии остановите локального бота с тем же Telegram-токеном.
   Блокировка в одной БД не защищает две независимые базы от работы с одним Telegram-ботом.
7. Откройте `<ваш-домен>/healthz`, дождитесь `status=ok`.
   POST `/telegram/webhook` без секретного заголовка должен вернуть 401;
   GET `/api/reports/unknown` без персонального токена — 401.
   В Telegram `getWebhookInfo`: правильный HTTPS-адрес, нет ошибки доставки;
    получите НОВУЮ ссылку `/report`
   в боте, откройте с телефона без компьютера и повторите раздел 7.
8. Перезапустите Railway-сервис: черновики должны остаться. Перезапуск production проверен:
   сохранились 10 отчётов, 9 операций, 12 ссылок и история. Проверка LLM из контейнера
   распознала `EM3-002=56` без создания отчёта и внешних записей.
9. Railway отклонил настройку автоматических резервных копий: доступны только Pro.
   Тариф не изменялся. Локально сохранены `data/before-railway-20261108.dump`
   (перед переносом, PostgreSQL 16) и `data/railway-postgres18-20261108.dump`
   (экспорт облачной базы, PostgreSQL 18). Восстанавливайте их в отдельную пустую
   базу соответствующей/новой версии с `pg_restore`, затем проверяйте записи.
   Файлы содержат реальные данные и исключены из Git.

Справка Railway: [PostgreSQL](https://docs.railway.com/databases/postgresql),
[healthchecks](https://docs.railway.com/deployments/healthchecks),
[переменные](https://docs.railway.com/variables).

## Критерий завершения

- Автотесты, проверка стиля и сборка проходят.
- 30 эталонных фраз и два диалоговых прогона проходят на выбранной модели.
- На изолированном стенде проверены превышение, частичный сбой и повтор без дубля.
- С настоящего телефона пройден путь до записи и исправления в обеих системах.
- После перезапуска сохранены черновики, ссылки и незавершённые операции.
- Посторонний пользователь не видит и не меняет отчёт.

Последние два внешних этапа — реальные голосовые с телефона и проверка Railway после
публикации — выполняются отдельно; автоматические тесты не заменяют их.
